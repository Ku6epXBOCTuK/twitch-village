# Архитектура twitch-village

**Статус:** Draft (принято к реализации) **Дата:** 2026-10-21 **Продукт:**
виджет для OBS «деревня зрителей» (аналог Stream Avatars для Twitch)

Документ объединяет прежние `widget-arch.md` (архитектура виджет-системы) и
`effect-ts.md` (оценка применимости Effect-TS) и фиксирует решения, принятые
после их обсуждения. Пошаговый план реализации — в `docs/ROADMAP.md`.

---

## 1. Контекст и цель

Нужна виджет-система для OBS: в сцене живут аватары зрителей, которые появляются
по событиям Twitch (вход в чат, сообщение, подарок) и остаются на экране как
обитатели деревни.

Требования:

- **Надёжность.** Сломанный виджет не должен ломать рендер остальных виджетов и
  трансляцию.
- **Горячее переключение виджетов** на ходу.
- **Изоляция.** Логика виджета живёт в отдельном Worker'е с первого дня: ни
  бесконечный цикл, ни OOM не касаются рендера.
- **Расширяемость.** Виджет может быть написан на JS или WASM без потери
  функциональности рендера.
- Сложность не является ограничением: архитектура намеренно строгая ради запаса
  надёжности и обучающей ценности.

Ключевая проблема: если рендер внутри виджета — сломанный виджет ломает рендер.
Если рендер вынесен в ядро — нужно решить, как изолированный виджет, у которого
нет доступа ни к DOM, ни к GPU-контексту, ни к `PIXI.Assets`, управляет
картинками, анимациями, шейдерами и фильтрами.

## 2. Принятое решение

**Render Core + командный протокол.** Виджет — изолированный «мозг», который
отправляет декларативные команды. Render Core — единственный владелец
`PIXI.Application`, `PIXI.Assets` и GPU-контекста, единственный, кто создаёт и
удаляет объекты сцены.

Уточнения, принятые для v1:

1. **PixiJS — единый инстанс в главном потоке.** Вынос Core в Worker
   (`OffscreenCanvas`) не нужен вообще и не планируется: он даёт только
   дополнительную задержку и известные проблемы PixiJS v8 с фильтрами в
   WebWorker. Изоляцию обеспечивает Worker на каждый виджет — этого достаточно
   для главного требования.
2. **Каждый виджет — отдельный Web Worker** с первого дня, не «модуль в том же
   потоке».
3. **Контракт типизирован через Effect-TS** (`Data.TaggedEnum` для команд,
   `Data.TaggedError` для ошибок, `Schema` для валидации на границе). Effect не
   проникает в рендер-цикл PixiJS и в логику виджета.
4. **Первый виджет — «деревня»**, отдельный пакет монорепо.
5. **Источник событий Twitch в v1 — мок.** Реальная интеграция (EventSub или
   IRC) подключается позже за тем же интерфейсом.

### 2.1. Компоненты

**Render Core** (`packages/core`, главный поток)

- Единственный владелец `PIXI.Application`, `app.stage`, `PIXI.Assets`.
- Не знает, что именно рисует виджет. Исполняет примитивы: создать узел,
  поставить спрайт, проиграть анимацию, сдвинуть, навесить фильтр, удалить.
- Валидирует каждую команду; невалидная — типизированная ошибка в лог, команда
  отбрасывается, Core продолжает работу.
- Каждый виджет получает собственный корневой `PIXI.Container`; всё, что делает
  виджет, происходит внутри него.
- Владеет реестрами ассетов и эффектов; виджет оперирует только ID.

**Widget Worker** (`packages/widget-village`, по одному экземпляру на виджет)

- Логика (мир, состояния, таймеры, реакция на события) на JS (позже — WASM).
- Нет доступа к PixiJS, DOM, GPU, сети, `PIXI.Assets`.
- Получает события Core через `postMessage`, отправляет команды рендера.
- При падении (ошибка, зависание, OOM) Core перестаёт получать heartbeat,
  помечает виджет сломанным, скрывает его контейнер; остальные виджеты и рендер
  не затронуты.

**Asset Pipeline**

- Ассеты каждого виджета собираются `@assetpack/core` (pipes `pixiPipes`) в
  атласы и `manifest.json` в формате PixiJS v8.
- Один бандл на виджет. Загрузка — при активации виджета, выгрузка — при
  деактивации.
- Манифест ассетов — контракт: виджет знает только строковые `assetId`.

**Effect Registry**

- Шейдеры и фильтры — ресурсы Core. Виджет не передаёт GLSL-код, только
  `effectId` и значения uniform'ов.
- Каждый виджет поставляет `effects.manifest.json`: `effectId`, исходник
  вершинного/фрагментного шейдера, схема параметров с границами.
- Добавление нового эффекта не требует правок Core — только записи в манифесте.
- Валидация параметров по схеме до применения; невалидное значение — команда
  отбрасывается.

**Scene Manager** (часть Core)

- Горячее переключение: активация/деактивация виджета = загрузка/выгрузка бандла
  - спавн/терминирование Worker'а + показ/скрытие корневого контейнера.
- `PIXI.Application` не пересоздаётся никогда.

### 2.2. Поток данных

```
event-mock  ──►  Core (EventBus)
                   │  postMessage(WidgetEvent)
                   ▼
             Widget Worker (мир деревни, фикс. тик 10 Гц)
                   │  postMessage(RenderCommand[])
                   ▼
        Validator (Effect Schema) ──► CommandQueue (per widget, bounded)
                   │
                   ▼  drain в app.ticker (бюджет: команд и мс на кадр)
        PIXI.Container виджета ──► Sprite / AnimatedSprite / Text / Filter
```

Обратное направление (Core → виджет): события зрителей, изменение размера канвы,
пауза/возобновление при деактивации, запрос на выгрузку.

### 2.3. Модель работы с ассетами и эффектами

Виджет не «получает картинку» и не создаёт `PIXI.Filter`. Он отправляет:

```ts
{ type: "SetSprite", nodeId: "avatar-42", assetId: "avatar/cat-idle-0" }
{ type: "SetAnimation", nodeId: "avatar-42", assetIds: [...], fps: 8 }
{ type: "AddFilter", nodeId: "avatar-42", effectId: "glow_pulse" }
{ type: "SetFilterParam", nodeId: "avatar-42", effectId: "glow_pulse", param: "uIntensity", value: 0.8 }
```

Core: ищет `assetId`/`effectId` в своём реестре → создаёт или обновляет объект
внутри контейнера виджета → при промахе логирует типизированную ошибку и
пропускает команду.

## 3. Монорепозиторий

pnpm workspaces + Turborepo. Сборка приложений — Vite, типы — `tsc -b` с project
references, тесты — Vitest.

```
twitch-village/
├─ apps/
│  └─ overlay/                 OBS browser source: страница, bootstrap Core, debug-панель
├─ packages/
│  ├─ protocol/                контракт Core ↔ Widget: команды, события, ошибки, схемы, версия
│  ├─ core/                    Render Core: Pixi, реестры, WidgetHost, CommandBus, SceneManager
│  ├─ widget-village/          виджет «деревня»: worker-энтри, мир, тик, ассеты, эффекты
│  ├─ event-mock/              мок-источник событий зрителей
│  └─ config/                  общие tsconfig, eslint, vitest-пресеты
├─ turbo.json
├─ pnpm-workspace.yaml
└─ docs/
```

### 3.1. Правила границ (проверяются линтером зависимостей)

| Пакет            | Может импортировать                       | Запрещено                                         |
| ---------------- | ----------------------------------------- | ------------------------------------------------- |
| `protocol`       | `effect`                                  | `pixi.js`, `core`, любые виджеты                  |
| `core`           | `protocol`, `pixi.js`                     | конкретные виджеты (только через реестр)          |
| `widget-village` | `protocol`                                | `pixi.js`, `core`, DOM-API (`document`, `window`) |
| `event-mock`     | `protocol`                                | `core`, `pixi.js`                                 |
| `overlay`        | `core`, `protocol`, `event-mock`, виджеты | бизнес-логика виджетов                            |

`core` не импортирует `widget-village`: активация виджета описывается
дескриптором (`WidgetDefinition` + URL воркера), который передаёт приложение.
Это и есть точка горячего переключения.

### 3.2. Почему Worker на каждый виджет, а не модуль в том же потоке

Изоляция по-настоящему: зависший цикл и утечка памяти не трогают рендер,
`terminate()` — гарантированная остановка. Ограничение — асинхронный канал и
необходимость watchdog. Взамен виджеты можно писать на WASM и перезапускать
независимо.

## 4. Протокол

Пакет `protocol` — единственный источник правды. Всё описано через
`Data.TaggedEnum` и `Schema`; сообщения сериализуемы в structured clone (никаких
классов, функций, `Map` с объектными ключами).

### 4.1. Версия

Каждое сообщение несёт `protocolVersion` (число). Core и Worker проверяют
совпадение мажорной версии; при несовпадении виджет не активируется с ошибкой
`ProtocolMismatch`. Изменение набора команд = инкремент версии.

### 4.2. Команды Widget → Core (`RenderCommand`)

| Тип              | Поля                                                                          |
| ---------------- | ----------------------------------------------------------------------------- |
| `CreateNode`     | `nodeId`, `kind` (`container` \| `sprite` \| `text`)                          |
| `SetParent`      | `nodeId`, `parentId \| null`, `order`                                         |
| `SetTransform`   | `nodeId`, `x?`, `y?`, `scaleX?`, `scaleY?`, `rotation?`, `alpha?`, `visible?` |
| `SetSprite`      | `nodeId`, `assetId`                                                           |
| `SetAnimation`   | `nodeId`, `assetIds[]`, `fps`, `loop`                                         |
| `SetText`        | `nodeId`, `text`, `style` (`fontSize`, `fill`, `align`)                       |
| `AddFilter`      | `nodeId`, `effectId`                                                          |
| `SetFilterParam` | `nodeId`, `effectId`, `param`, `value`                                        |
| `RemoveFilter`   | `nodeId`, `effectId`                                                          |
| `RemoveNode`     | `nodeId`                                                                      |
| `Batch`          | `commands: RenderCommand[]` — атомарная пачка на тик                          |
| `Ready`          | `widgetId`, `protocolVersion` — воркер поднялся                               |
| `Heartbeat`      | `tick`                                                                        |

`nodeId` — локальный для виджета; Core хранит их в пространстве имён экземпляра
(`village#1:avatar-42`), поэтому два экземпляра одного виджета не конфликтуют.

### 4.3. События Core → Widget (`WidgetEvent`)

| Тип           | Поля                                   |
| ------------- | -------------------------------------- |
| `Init`        | `widgetId`, `config`, `viewport {w,h}` |
| `ViewerEvent` | `event` (см. 4.4)                      |
| `Viewport`    | `w`, `h`                               |
| `Pause`       | —                                      |
| `Resume`      | —                                      |
| `Dispose`     | —                                      |

### 4.4. События зрителей (`ViewerEvent`)

Типизированное подмножество Twitch, достаточное для деревни:

- `ViewerJoined` — `viewerId`, `displayName`, `color?`
- `ViewerMessage` — `viewerId`, `text`, `isCommand`
- `ViewerGift` — `viewerId`, `amount`, `kind` (`bits` \| `sub` \| `giftSub`)
- `ViewerLeft` — `viewerId`

В v1 их генерирует `event-mock`. Реальная интеграция позже мапит EventSub/IRC в
эти же типы — виджет не заметит разницы.

### 4.5. Транспорт

```ts
interface Transport {
  send(message: WidgetToCore): void;
  subscribe(handler: (message: CoreToWidget) => void): () => void;
  dispose(): void;
}
```

- `WorkerTransport` (Core и воркер) — обёртка над `postMessage`/`MessagePort`.
- `DirectTransport` (только тесты) — синхронная передача в том же потоке.
- Виджет получает `Transport`, а не глобальный `self`, поэтому тестируется без
  воркера.

## 5. Внутренности Core

### 5.1. WidgetHost

На каждый активированный виджет: `Worker`, `Transport`, корневой
`PIXI.Container`, `NodeRegistry` (локальные ID → Pixi-объекты), очередь команд,
watchdog, состояние:

```
loading → active → (paused) → active
                ↘ degraded (ошибки валидации / флуд)
                ↘ crashed  (ошибка воркера / таймаут heartbeat)
```

Переход в `crashed`: `worker.terminate()`, контейнер `visible = false`, очередь
сбрасывается, счётчики в статус. Восстановление — явная реактивация (кнопка в
debug-панели), без автоциклов в v1.

### 5.2. CommandBus

- Очередь FIFO на виджет, лимит `maxQueueLength` (например 4096 команд).
- Переполнение → пачка отбрасывается, виджет → `degraded`, событие в лог.
- Дренаж в `app.ticker`: не более `maxCommandsPerFrame` (например 512) и не
  более `maxDrainMs` (например 4 мс) за кадр. Остаток — на следующий кадр.
- Каждая команда проходит валидацию `Schema`; ошибка типизирована и
  инкрементирует счётчик виджета, но не прерывает обработку остальных.

### 5.3. NodeRegistry и границы ошибок

- Все Pixi-объекты виджета создаются только здесь, внутри контейнера виджета.
- Любая операция над узлом в `try/catch` на уровне команды: исключение Pixi
  превращается в `RenderFailed` и отбрасывается.
- Неизвестный `nodeId`, дубликат `CreateNode`, удаление несуществующего узла —
  `InvalidCommand`.

### 5.4. AssetRegistry

- `Assets.init({ manifest })` один раз при старте приложения; манифест
  собирается из манифестов пакетов-виджетов (бандл на виджет).
- `loadBundle(bundleId)` при активации, `unloadBundle` при деактивации.
- `assetId` вне загруженного бандла → `AssetNotFound`.
- Политика выгрузки v1: сразу при деактивации (без LRU).

### 5.5. EffectRegistry

- Манифест эффектов пакета виджета загружается при активации.
- Шейдер компилируется лениво при первом `AddFilter`; ошибка компиляции →
  `EffectCompileFailed`, эффект помечается сломанным, повторные попытки не
  выполняются до реактивации.
- Значения uniform'ов проверяются схемой с границами (`min`/`max`); значение вне
  диапазона → `InvalidEffectParam`, команда отбрасывается.
- Экземпляр `Filter` кэшируется на узел, чтобы не пересоздавать ресурсы каждый
  кадр.

### 5.6. Watchdog

- Воркер шлёт `Heartbeat` каждые 500 мс, Core ожидает следующий не позже 2000
  мс.
- Также слушаются `worker.onerror` и `messageerror`.
- Таймаут или ошибка → `WidgetCrashed`/`WidgetTimeout` → `terminate()`,
  контейнер скрыт, статус в панели.
- Падение воркера никогда не бросает исключение в тикер Core.

### 5.7. SceneManager

```ts
interface WidgetDescriptor {
  id: string;
  workerUrl: URL;
  assetBundle: string;
  effectsManifest?: URL;
  config?: unknown;
}

interface SceneManager {
  activate(descriptor: WidgetDescriptor): Promise<void>;
  deactivate(widgetId: string): Promise<void>;
  status(widgetId: string): WidgetStatus;
}
```

Активация идемпотентна (повторная — no-op или перезапуск по флагу), деактивация
освобождает бандл и воркер. Порядок узлов в `stage` задаётся `zIndex` корневых
контейнеров.

## 6. Ошибки

Все ошибки — `Data.TaggedError`, объявлены в `protocol`.

| Ошибка                | Источник           | Политика                           |
| --------------------- | ------------------ | ---------------------------------- |
| `InvalidCommand`      | валидация схемы    | отбросить команду, лог, счётчик    |
| `UnknownNode`         | NodeRegistry       | отбросить команду, лог             |
| `AssetNotFound`       | AssetRegistry      | отбросить команду, лог             |
| `EffectNotFound`      | EffectRegistry     | отбросить команду, лог             |
| `EffectCompileFailed` | компиляция шейдера | пометить эффект сломанным, лог     |
| `InvalidEffectParam`  | проверка uniform   | отбросить команду, лог             |
| `RenderFailed`        | исключение Pixi    | отбросить команду, лог             |
| `QueueOverflow`       | CommandBus         | сброс очереди, виджет → `degraded` |
| `WidgetTimeout`       | watchdog           | `terminate()`, контейнер скрыт     |
| `WidgetCrashed`       | `worker.onerror`   | `terminate()`, контейнер скрыт     |
| `ProtocolMismatch`    | handshake          | не активировать виджет             |

Правило: ни одна ошибка виджета не приводит к остановке ticker'а Core. Ошибки
собираются в `WidgetStatus` (`counters` по тегам) и видны в debug-панели.

## 7. Виджет «деревня» (v1)

### 7.1. Модель мира

- `Viewer` — `id`, `displayName`, `color`, `avatarIndex`, `position`,
  `velocity`, `state` (`idle` \| `walk` \| `celebrate`), `expiresAt`.
- Мир ограничен viewport'ом; у краёв — отражение/перевыбор цели.
- Фиксированный шаг: 10 Гц (`dt = 100 мс`), накопитель времени, чтобы не
  зависеть от частоты `setInterval`.
- `ViewerJoined` → спавн в случайной точке у нижней кромки.
- `ViewerMessage` → смена состояния на `celebrate`/реплика над головой.
- `ViewerGift` → `celebrate` + масштаб/эффект по величине подарка.
- `ViewerLeft` → плавное исчезновение и удаление узлов.
- Пауза при `Pause`: тик останавливается, состояние сохраняется.

### 7.2. Генерация команд

- Dirty-check по сущностям: команды только для изменившихся, пачкой `Batch` раз
  в тик.
- На сущность: контейнер → спрайт (аватар) + текст (имя) + опциональный фильтр.
- Никакой логики Pixi: только `nodeId`, `assetId`, числа.

### 7.3. Ассеты и эффекты

- `packages/widget-village/assets/` — плейсхолдер-спрайты (32×32, 4 кадра на
  аватар), собираются `@assetpack/core` (`pixiPipes`) в атлас + `manifest.json`
  (`manifest.webmanifest`/`manifest.json` формата PixiJS v8).
- `effects.manifest.json` — минимум один эффект (`glow_pulse`) для проверки
  реестра фильтров.

## 8. Приложение и наблюдаемость

### 8.1. `apps/overlay`

- `index.html` — единственная страница, грузит bootstrap: создаёт
  `PIXI.Application` (resize на размер окна), инициализирует Core, регистрирует
  дескриптор деревни, подписывает `event-mock`.
- В OBS используется как Browser Source с URL Vite-превью (dev) или собранного
  `dist` (prod).
- `?widgets=village&debug=1` — конфиг через query-параметры.

### 8.2. Debug-панель v1

HTML-оверлей в правом верхнем углу той же страницы, включается `?debug=1`:

- статус и счётчики ошибок по виджетам;
- кнопки «спавн зрителя», «сообщение», «подарок», «уволить всех»;
- «деактивировать/активировать виджет» — проверка горячего переключения;
- «убить воркер» — проверка watchdog и изоляции.

Панель общается с Core напрямую (тот же модуль). Отдельная страница-пульт
(`control.html`) — вне v1: OBS-источник живёт в отдельном процессе, для связи
нужен сервер; это отдельное решение, не блокирующее деревню.

### 8.3. `event-mock`

- `MockEventSource` по интерфейсу `ViewerEventSource`:
  `subscribe(handler): () => void`, `start(config)`, `stop()`.
- Режимы: ручной (события из debug-панели) и авто (интервал, случайные имена).
- Детерминированный PRNG с seed — для воспроизводимых смоук-тестов.

## 9. Сборка, типы, тесты

- **Turborepo**: задачи `build`, `dev`, `typecheck`, `test`, `lint`, `assets` с
  корректными `dependsOn` и `outputs`.
- **Vite** для `apps/overlay`; воркер виджета — отдельная точка входа,
  подключается как `new Worker(new URL(...), { type: "module" })`.
- **tsc -b** с project references: `protocol` → `core`/`widget-village` →
  `overlay`.
- **Vitest**:
  - `protocol` — сериализация/десериализация, схемы (валидные/невалидные),
    совместимость версий;
  - `core` — CommandBus (бюджет, переполнение), NodeRegistry (дубликаты,
    неизвестные узлы), EffectRegistry (границы uniform'ов) на фейковом
    Pixi-стабе без GPU;
  - `widget-village` — мир на `DirectTransport`: спавн/тик/удаление, стабильное
    число команд, детерминизм по seed;
  - `event-mock` — генерация событий по seed;
  - смоук — сборка overlay + проверка, что активация/деактивация не течёт (число
    воркеров и контейнеров возвращается к нулю).
- **Линт границ** — `dependency-cruiser` или `eslint-plugin-boundaries` с
  правилами из 3.1 (в v1 достаточно одного набора запретов).

## 10. Рассмотренные альтернативы

**Виджет + собственный PixiJS в том же Worker (`OffscreenCanvas`).** Технически
возможен, но «сломанный виджет» = «сломанный рендер» в одном контексте; теряется
главное требование. Плюс дублирование загрузки ассетов и риск исчерпания лимита
WebGL-контекстов (8–16 на страницу).

**Рендер в каждом виджете без Worker.** Быстрый выход за лимит контекстов,
дублирование логики ассетов, падение виджета подвешивает страницу.

**Render Core в Worker (`OffscreenCanvas`).** Не даёт выигрыша для нашей
нагрузки, добавляет задержку `postMessage` и известные проблемы PixiJS v8 с
фильтрами в WebWorker (`window`-зависимости вроде `TwistFilter`, баги сборок).
Отклонено: Core остаётся в главном потоке.

**Виджеты как модули в главном потоке (без Worker).** Проще и быстрее, но
зависший виджет блокирует кадр. Отклонено, потому что изоляция — главное
требование.

**Эффекты: B — шейдер как ассет с кодом от виджета; C — whitelist + отложенная
регистрация.** Оба гибче, но небезопаснее манифеста: код шейдера приходит из
пакета вида, который может поставляться третьей стороной. В v1 — манифест
эффектов, поставляемый вместе с пакетом виджета; компиляция только в Core.

## 11. Effect-TS: где применяем, где нет

Применяем:

- `Data.TaggedEnum` — команды и события (исчерпывающий `match`).
- `Data.TaggedError` — каталог из раздела 6, восстановление через `catchTag`.
- `Schema` — валидация на границе Worker → Core (decode, а не ручные проверки).
- `Effect.gen` для оркестрации активации: загрузить бандл → загрузить манифест
  эффектов → поднять воркер → дождаться `Ready` с таймаутом.
- `Scope`/`acquireRelease` — опционально, там где ресурс обязан освободиться
  (бандл, воркер). Вводится в фазе надёжности, не блокирует v1.

Не применяем:

- Рендер-цикл PixiJS: `app.ticker.add` остаётся императивным.
- Логика виджета в воркере: `postMessage` и цикл мира пишутся на чистом TS.
  Единственное исключение — сложная JS-обвязка над WASM.
- `@effect/rpc` в v1: ручной протокол на `TaggedEnum` + `postMessage` проще
  отлаживается. Пересмотреть, если набор команд вырастет настолько, что ручные
  хендлеры станут источником ошибок.

Цена: ~25 КБ gzip рантайма Effect в Core и `overlay`. Для OBS-оверлея приемлемо.

## 12. Риски

| Риск                              | Смягчение                                                     |
| --------------------------------- | ------------------------------------------------------------- |
| Флуд команд от сломанного воркера | bounded queue, бюджет на кадр, `degraded`                     |
| Зависание воркера без исключения  | heartbeat + таймаут + `terminate()`                           |
| Утечка памяти при переключениях   | `unloadBundle`, `terminate()`, смоук на счётчики              |
| Ошибки компиляции шейдеров        | ленивая компиляция, `EffectCompileFailed`, изоляция на эффект |
| Structured clone не умеет классы  | только plain-объекты в протоколе, тест сериализации           |
| Разные версии протокола у пакетов | `protocolVersion` + `ProtocolMismatch`                        |
| DPI/масштаб в OBS                 | расчёт по `devicePixelRatio`, `resizeTo: window`, тест в OBS  |
| Версии PixiJS/Effect меняются     | версии фиксируются в `Ф0`, апгрейд — отдельным шагом          |

## 13. Открытые вопросы (вне v1)

- Реальная интеграция Twitch: EventSub через свой Node-сервер или IRC-клиент в
  браузере; где хранится конфиг канала и токены.
- Отдельная страница-пульт: нужен транспорт между OBS-источником и пультом
  (WebSocket-сервер).
- WASM-виджет: нужен ли и на каком примере проверять.
- Политика кастомных шейдеров от третьих сторон: разрешать ли код в манифесте
  или только предустановленный набор.
- Персистентность состояния деревни между перезапусками OBS.
- Политика выгрузки бандлов при многих виджетах (LRU вместо «сразу»).
