# AGENTS.md — правила работы над twitch-village

## 1. Что это за проект

Виджет для OBS «деревня зрителей» (аналог Stream Avatars для Twitch): аватары
зрителей живут в сцене, появляются по событиям чата (вход, сообщение, подарок),
ходят, реагируют и остаются на экране.

Ключевое архитектурное решение: **Render Core + командный протокол**.

- `@tv/core` — единственный владелец `PIXI.Application`, `PIXI.Assets` и GPU.
  Исполняет декларативные команды, ничего не знает о смысле виджета.
- Каждый виджет — **отдельный Web Worker**. У него нет DOM, Pixi, GPU, сети. Он
  получает события и отправляет команды вида `CreateNode` / `SetTransform` /
  `SetAnimation`.
- `@tv/protocol` — единственный источник правды по контракту (Effect `Schema`,
  `Data.TaggedError`, `Transport`).
- Отказ виджета (ошибка, зависание, OOM) не должен ломать рендер и трансляцию:
  watchdog, `terminate()`, скрытие контейнера, `crashed` в статусе.

Подробности и принятые решения: `docs/ARCHITECTURE.md`. Пошаговый план:
`docs/ROADMAP.md`. Точные поля схем — только в `packages/protocol/src`, в
документации их дублировать не нужно.

Пакеты: `@tv/protocol`, `@tv/core`, `@tv/widget-village`, `@tv/event-mock`,
`@tv/config`, приложение `@tv/overlay`. Монорепо: pnpm + Turborepo, Vite,
Vitest, TypeScript 5.9, Effect 4, PixiJS 8.

## 2. Распределение работы

Проект учебный: цель не «получить код», а **научиться писать основную логику**.

**Агент пишет:**

- бойлерплейт: конфиги, `tsconfig`, ESLint, Vite, assetpack, `package.json`;
- объявления типов, схемы, интерфейсы, каталоги ошибок, константы;
- тесты: каркас `describe`/`it`, фабрики, фейки (`fake-render-target`,
  `DirectTransport`), контрактные наборы;
- обвязку без доменных решений: экспорты, регистрация, wiring.

**Пользователь пишет основную логику:** алгоритмы и правила поведения — шаг
мира, dirty-check и генерация команд, дренаж очереди, реестры, оркестрация
жизненного цикла, watchdog, шейдеры. Агент такие файлы **не заполняет**, даже
если может.

Порядок шага:

1. Агент объявляет границы шага: файлы, сигнатуры, тесты (падающие/красные —
   нормально).
2. Пользователь пишет реализацию.
3. Агент прогоняет проверки и выдаёт замечания (§4) — без правок логики за
   пользователя.

Если пользователь просит сделать шаг «целиком», агент делает бойлерплейт и
тесты, а логику оставляет `TODO`-заглушкой с сигнатурой и **сообщает об этом**,
не заполняя её молча.

### 2.1. Проверяет агент, а не пользователь

Всё, что можно проверить инструментом, агент проверяет сам: `typecheck`, `lint`,
`test`, `goh comments`, сборку, запуск скрипта, чтение вывода. Никаких «теперь
прогони тесты», «проверь, что линтер чистый», «посмотри, что в консоли» — это
работа агента, а не шаг для пользователя.

- Проверки идут после каждой порции правок, а не один раз в конце.
- Падение разбирается до конца: агент читает ошибку, находит причину, чинит
  обвязку и сообщает, если причина в учебной логике пользователя.
- В ответе показывается результат команд (что запускалось, что ответило), а не
  просьба их запустить.
- К пользователю уходят только решения и действия, которые требуют его рук:
  выбор варианта, написание логики, ручной смоук в браузере или OBS.
- Если инструмент недоступен (нет бинаря, нет GPU, нет OBS) — это называется
  прямо, вместе с тем, что именно осталось непроверенным.

## 3. Режим подсказок

Когда пользователь просит подсказку, агент **не даёт код**. Разрешено:

- назвать функцию, метод, оператор, класс, тип (`Effect.forEach`,
  `Schema.decodeUnknownSync`, `RenderTarget.setParent`, `Match.valueTags`);
- объяснить, где это лежит: файл, пакет, раздел `docs/`;
- описать порядок шагов словами или псевдокодом без синтаксиса проекта;
- указать на инвариант или тест, который должен пройти;
- задать встречный вопрос, если задача недоопределена.

Запрещено: готовые блоки кода, «просто вставь это», переписывание файла целиком.
Код показывается только по явной просьбе («покажи код»), и тогда — минимальный
фрагмент, а не решение задачи.

Подсказка идёт по возрастанию: намёк → имя API → шаги → псевдокод. Одна
подсказка за раз, следующая — после ответа пользователя.

## 4. Проверка конца шага

В конце каждого шага (после `typecheck`/`lint`/`test`) агент выдаёт замечания
списком. Формат строки:
`файл:строка — тег — что не так — как принято в проекте`.

Теги: `effect`, `pixi`, `ts`, `arch`, `test`.

### **effect-way**

- `Layer`/`ManagedRuntime` — только в `core/src/live.ts`; `runSync` — только в
  `core/src/effect-adapter.ts`. Нарушение = `arch`.
- Эффекты собираются через `Effect.fn`/`Effect.fnUntraced`, ошибки уходят в
  `E`-канал (`Effect.fail`), а не в `throw`; исключения чужих API ловятся
  `Effect.try`, а не `try/catch`.
- Границы валидируются `Schema` (decode на входе, не ручные проверки полей);
  разбор вариантов — `Match.valueTags`/`Match.tag` без `default`.
- Ошибки — только `Data.TaggedError` из `protocol`, с `widgetId` и контекстом.
- Сервисы берутся из `Context` внутри `Effect.gen`, а не прокидываются
  параметрами или глобальными переменными.
- Pixi-слой и виджет не видят рантайм Effect (только типы).

### **pixi-way**

- Pixi-объекты создаёт и удаляет только Core (внутри `RenderTarget` и
  `NodeRegistry`); виджет и `apply-command` работают с `nodeId` и числами.
- Текстуры и фильтры — из реестров по `assetId`/`effectId`; никаких ручных
  `Texture.from`, `Assets.load` по месту.
- Удаление поддерева, смена родителя, порядок (`order`/`zIndex`), частичный
  `SetTransform` — через контракт `RenderTarget`, обе реализации (`pixi` и
  `fake`) обязаны проходить `render-target.contract.ts`.
- Никакой работы в кадре сверх бюджета: лимит команд и миллисекунд на кадр,
  пустой кадр не аллоцирует.

### **typescript-way**

- `strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`: не
  ослаблять типами (`any`, `!`, лишние `as`), не отключать правила линтера.
- Дискриминированные объединения вместо флагов; `readonly` для данных, которые
  не мутируются; `verbatimModuleSyntax` — `import type` для типов.
- Брендированные ID (`NodeId`, `AssetId`, `WidgetId`) не приводятся к `string`
  без нужды; границы — `Schema`, а не касты.
- Экспорт — только то, что нужно снаружи пакета.

### **test**

- Тесты не требуют GPU, браузера и реального воркера: фейковый рендер-таргет,
  `DirectTransport`, инжектируемое время.
- Время и случайность детерминированы (`now`, seed); тест не спит.
- Имя теста описывает поведение, а не вызов функции.

Замечания не исправляются молча: сначала список, правки — по решению
пользователя. Если замечание касается его учебного кода, агент объясняет
причину, но код не переписывает.

## 5. Инварианты, которые нельзя нарушать

- `pixi.js`, `@tv/core` и DOM (`window`, `document`) недоступны из
  `widget-village`; `core` не импортирует конкретные виджеты.
- `PIXI.Application` не пересоздаётся при переключении виджетов.
- Сообщения протокола — plain-объекты, сериализуемые `structuredClone` (никаких
  классов, функций и `undefined` в значениях).
- Изменение набора команд = инкремент `PROTOCOL_VERSION`.
- Ошибка виджета не останавливает ticker Core и не ломает другие виджеты.
- Версии библиотек фиксированные (§9.1 архитектуры); апгрейд — отдельный шаг.

## 6. Команды

```sh
pnpm install
pnpm typecheck          # turbo typecheck по всем пакетам
pnpm lint
pnpm test
pnpm dev                # apps/overlay
pnpm -F @tv/core test   # адресно, то же для остальных пакетов
```

`pnpm assets` падает до появления `.assetpack.js` (фаза 4) — это ожидаемо. Типы
между пакетами идут через `package.json` (`"types": "./src/index.ts"`), project
references не используются.

## 7. Соглашения репозитория

- Код, тесты и имена — английский; документация и общение — русский.
- Отступы и форматирование — Prettier из корня, без локальных настроек.
- Комментариев нет. Единственное исключение — `// NOTE:` (до 3 строк, ASCII), и
  только там, где причина неочевидна из кода.
- `docs/ROADMAP.md` может отставать от кода: статус шага сверяется с `git log` и
  фактическими файлами, а не только с отметкой в документе.
- Задачи и находки — в локальном трекере `XBOCT-log`, проект `twitch-village`
  (префикс `TV`). Ссылки на задачи — полным id, например `TV-42`.
- Ошибка или шероховатость, найденная по ходу шага и не блокирующая его, не
  правится как побочный эффект: она заводится задачей в трекере.

## 8. Заглушки вместо недосказанного

Если требования шага противоречат `docs/ARCHITECTURE.md` или оставляют выбор,
агент не выбирает молча: он перечисляет варианты (до 3), называет последствия и
ждёт решения. Архитектурное решение, принятое по ходу, фиксируется в
`docs/ARCHITECTURE.md` отдельным изменением.
